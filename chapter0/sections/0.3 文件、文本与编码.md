# 0.3 文件、文本与编码

这一节解决两个常见困惑：

- 为什么说“文件里其实没有文字，只有字节”？
- 为什么同一个中文文件，在 Windows 记事本和 Linux 终端里可能一个正常、一个乱码？

## 0.3.1 文件本质上是一串字节

不管是 `.c` 源文件、图片、视频还是一个可执行文件，在硬盘上都可以看成一段字节序列。

字节是 8 个二进制位，取值从 0 到 255。文件内容就是这些字节按顺序排列。

我们平时说“这是一个文本文件”，意思是：这些字节按照某种字符编码规则解释后，能得到人类可读的字符。

“二进制文件”通常指不能用普通文本编辑器直接阅读的文件，例如图片、压缩包、可执行文件。它不是“没有字节”，而是“这些字节不是按文本规则组织的”。

| 类型 | 例子 | 能否直接用文本编辑器读 |
|------|------|------------------------|
| 文本文件 | `.c`、`.md`、`.txt` | 通常可以 |
| 二进制文件 | 图片、音频、可执行文件、压缩包 | 通常不可以 |

## 0.3.2 字符、码点和编码

这里要区分三个概念：

- 字符：人类看到的一个符号，例如 `你`、`A`、`1`。
- 码点：字符在 Unicode 标准里的编号，例如 `你` 的码点是 U+4F60。
- 编码：把码点变成字节的规则，例如 UTF-8、GBK。

同一个字符，用不同编码保存，得到的字节可能不同。

以“你”为例：

| 编码 | 字节（十六进制） | 长度 |
|------|------------------|------|
| UTF-8 | `E4 BD A0` | 3 字节 |
| GBK | `C4 E3` | 2 字节 |

再比如“中”：

| 编码 | 字节（十六进制） |
|------|------------------|
| UTF-8 | `E4 B8 AD` |
| GBK | `D6 D0` |

所以，**一段字节本身并不自带“我是 UTF-8”的标签**。必须知道它用的是什么编码，才能正确还原成字符。

```mermaid
flowchart LR
    A["字符<br/>你"] --> B["码点<br/>U+4F60"]
    B --> C["UTF-8 编码"]
    C --> D["字节<br/>E4 BD A0"]
    D --> E["按 UTF-8 解码"]
    E --> F["显示字符<br/>你"]
```

如果拿 GBK 的字节去按 UTF-8 解码，或者反过来，就会得到乱码，甚至解码失败。

## 0.3.3 常见编码

| 编码 | 特点 | 常见场景 |
|------|------|----------|
| ASCII | 只覆盖英文字母、数字和少量符号，1 字节 | 早期英文文本、部分协议 |
| GBK | 中文编码，兼容部分 ASCII，中文通常 2 字节 | 简体中文 Windows 旧环境 |
| UTF-8 | Unicode 的一种变长编码，英文 1 字节，中文通常 3 字节 | 互联网、Linux、现代编辑器 |
| UTF-16 | Unicode 的另一种编码，常见 2 或 4 字节 | Windows 内部、部分文件格式 |

今天写新代码，优先使用 UTF-8。它兼容 ASCII，跨平台支持好，也是大多数现代工具和网站的默认选择。

### BOM 是什么

有些 Windows 程序保存 UTF-8 文件时，会在文件开头加三个字节：

```text
EF BB BF
```

这叫 UTF-8 BOM。BOM 本来是用来标记字节序的，但 UTF-8 没有字节序问题，所以很多工具不需要它。

BOM 可能导致一些问题：

- 某些编译器或脚本把 BOM 当成内容的一部分。
- 文件开头出现看不见的字符。
- 不同工具对 BOM 的处理不一致。

建议保存为“UTF-8 无 BOM”。大多数编辑器都有这个选项。

## 0.3.4 换行符：LF 和 CRLF

不同系统对“换行”的表示不一样：

| 名称 | 字节 | 常见系统 |
|------|------|----------|
| LF | `0A` | Linux、macOS |
| CRLF | `0D 0A` | Windows |

大多数现代编辑器能自动识别两种换行。但在跨平台协作时，混用可能导致：

- Git 显示整个文件都被修改。
- 某些脚本按行处理时多出一个 `\r`。
- 终端输出出现奇怪的覆盖行为。

建议在仓库里统一使用 LF，并通过 `.gitattributes` 或编辑器设置处理 Windows 检出时的转换。第 4 章讲多文件工程时会再提到。

## 0.3.5 路径、扩展名和权限

路径用来定位文件。分两种：

- 绝对路径：从根目录开始，例如 `/home/user/hello.c` 或 `C:\Users\user\hello.c`。
- 相对路径：从当前目录开始，例如 `./hello.c` 或 `../chapter1/README.md`。

两个常见符号：

- `.` 表示当前目录。
- `..` 表示上一级目录。

Windows 用反斜杠 `\` 分隔路径，Linux 和 macOS 用斜杠 `/`。在 C 语言字符串里，反斜杠是转义字符，所以 Windows 路径经常要写成 `C:\\Users\\user`，或者使用正斜杠 `C:/Users/user`。

扩展名只是文件名的一部分，用来提示文件类型：

- `.c`：C 源文件。
- `.h`：头文件。
- `.exe`：Windows 可执行文件。
- `.md`：Markdown 文档。

扩展名不能决定文件内容。把图片改名成 `.txt`，它仍然是图片。

Linux 还有可执行权限的概念。一个文件即使格式正确，如果没有执行权限，也不能直接运行。后面会用到：

```bash
chmod +x hello
./hello
```

## 0.3.6 中文为什么会在 Windows 控制台乱码

最常见的情况是：

- 源文件保存为 UTF-8。
- Windows 控制台默认使用 GBK（代码页 936）。
- 程序把 UTF-8 字节直接送到控制台，控制台按 GBK 解释，于是显示乱码。

解决办法通常有三个层次：

1. 源文件统一保存为 UTF-8 无 BOM。
2. 使用支持 UTF-8 的终端，例如 Windows Terminal。
3. 必要时把控制台代码页切到 UTF-8：

```bat
chcp 65001
```

也可以在程序里设置区域，但这通常不是初学阶段的首选。先保证“文件编码”和“终端编码”一致，大部分乱码就能解决。

> **Windows 提示**
>
> 如果中文输出乱码，先检查两件事：源文件是不是 UTF-8，终端代码页是不是 936。不要一开始就怀疑 C 语言或 `printf`。

## 0.3.7 小结

- 文件本质上是字节序列，文本文件需要按编码解释。
- 同一个字符在不同编码下字节不同。
- 新项目优先使用 UTF-8 无 BOM。
- Linux 用 LF，Windows 常用 CRLF，仓库里建议统一。
- 路径分绝对路径和相对路径，Windows 和 Linux 的分隔符不同。
- 中文乱码通常不是 C 语言的问题，而是文件编码和终端编码不一致。

## 练习

1. 为什么“把文件后缀从 `.png` 改成 `.txt`”不会让图片变成文本？
2. UTF-8 和 GBK 保存同一个汉字，字节数一定相同吗？
3. Windows 控制台显示中文乱码时，最先应该检查什么？

<details>
<summary>参考答案</summary>

1. 后缀只是文件名的一部分，文件内容仍然是原来的二进制数据；文本编辑器能否读懂取决于内容编码，不取决于后缀。
2. 不一定。例如“你”在 UTF-8 中是 3 字节，在 GBK 中是 2 字节。
3. 先检查源文件编码和终端代码页是否一致，常见情况是源文件 UTF-8、控制台 GBK。可以尝试使用 Windows Terminal 或 `chcp 65001`。

</details>
