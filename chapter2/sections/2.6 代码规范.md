# 2.6 代码规范

代码不只是给机器执行的，也是给人读的。这里的“人”包括未来的你。

这一节讲的是格式和习惯，不是新语法。很多规则看起来琐碎，但它们能减少一类很常见的 bug：代码看起来是一个意思，实际是另一个意思。

> **说明**
>
> 本书的代码风格参考 Linux 内核的编码习惯，但只采用适合用户态初学者教程的部分。`EXPORT_SYMBOL`、`kmalloc`、引用计数、sparse 等内核专用内容不会出现在示例里。

## 2.6.1 缩进

- 使用 Tab 缩进，Tab 宽度设为 4 或 8。

> **Tips**
> 如果你是在 GitHub 上查看，你可以在 **账户设置(Sittings) > 外貌(Appearance) > Tab 键宽度设置(Tab size preference) 修改成你喜欢的宽度。

- 不要用空格做缩进；注释、文档和 Markdown 表格除外。
- 一行只写一条语句。
- 一行只声明一个变量。
- 嵌套不要超过 4 层；超过就拆函数。

```c
int total = 0;
int count = 0;

for (int i = 0; i < 10; i++) {
	total += i;
	count++;
}
```

不要在一条语句里塞多个声明：

```c
int a = 1, b = 2, c = 3;
```

改成：

```c
int a = 1;
int b = 2;
int c = 3;
```

这样更容易逐个注释，也更容易在调试时看清楚每个变量。

## 2.6.2 行宽

每行不超过 100 列。

长表达式拆成多个有意义的片段，续行用空格对齐：

```c
printf("%s 的年龄是 %d，成绩是 %.1f\n",
       student.name, student.age, student.score);
```

如果这行语句已经有缩进，第二行补齐应该先用 Tab 补齐缩进，然后使用空格对齐

```c
do {
	printf("%s 的年龄是 %d，成绩是 %.1f\n",
	       student.name, student.age, student.score);
} while (false);
```

为了方便查看，用 (TAB) 代表 Tab，.代表空格，上面代码的示例是这样的:

```c
do {
(TAB)printf("%s 的年龄是 %d，成绩是 %.1f\n",
(TAB).......student.name, student.age, student.score);
} while (false);
```

不要为了凑行宽把用户可见的字符串拆开，否则不方便搜索：

```c
printf("这是一段很长的提示，"
       "不要随便拆开\n");
```

用户看到的字符串尽量保持完整。

## 2.6.3 大括号和空格

控制语句使用 K&R 风格：左大括号放在行尾。

```c
if (score >= 60) {
	printf("及格\n");
} else {
	printf("不及格\n");
}
```

函数例外：函数的左大括号另起一行。

```c
int add(int a, int b)
{
	return a + b;
}
```

`do-while` 和 `else` 与右大括号同行：

```c
do {
	...
} while (condition);

if (condition) {
	...
} else {
	...
}
```

### switch 的缩进

`switch` 和 `case` 左对齐，`case` 里面的语句缩进一层：

```c
switch (choice) {
case 1:
	do_one();
	break;
case 2:
	do_two();
	break;
default:
	break;
}
```

### 空格

- 关键字后加空格：`if (`、`for (`、`while (`、`switch (`、`return`。
- `sizeof`、`typeof`、`alignof` 后不加空格：`sizeof(struct student)`。
- 括号内不加多余空格。
- 指针 `*` 靠近变量名：`char *name;`
- 二元和三元运算符两侧加空格。
- 一元运算符后不加空格：`!done`、`-value`、`&data`。
- `.` 和 `->` 两侧不加空格。
- 行尾不留空白。

## 2.6.4 命名

- 变量和函数用小写加下划线：`student_count`、`calculate_total`。
- 不要用驼峰：`studentCount`、`calculateTotal`。
- 不要用匈牙利命名法：`iCount`、`strName`。
- 名字要有描述性。循环下标可以用 `i`、`j`，临时变量可以用 `tmp`，其他变量不要用 `a`、`b`、`x1` 这类名字。
- 常量宏和枚举标签用大写：`MAX_STUDENTS`、`COLOR_RED`。
- 函数名用动词开头：`print_student`、`read_file`、`is_valid`。

```c
int student_count = 0;
double average_score = 0.0;
```

不要写成：

```c
int sc = 0;
double avg = 0.0;
```

除非上下文非常清楚，否则缩写会让别人多花时间猜。

## 2.6.5 注释

注释解释“做什么”和“为什么”，不要逐行解释“怎么做”。

```c
// 计算所有学生的平均分，跳过缺考记录
double average = calculate_average(scores, count);
```

不要写：

```c
// 把 i 加 1
i++;
```

单行注释用 `//` 加一个空格，多行注释用 `/* ... */` 星号列风格：

```c
/*
 * 读取学生人数。
 * 如果文件为空，返回 0。
 */
int read_student_count(FILE *file)
{
	...
}
```

不要用多行 `//` 拼接多行注释。

可以适量使用 `TODO`、`FIXME` 标记待办：

```c
// TODO: 处理文件打开失败的情况
```

但不要用注释代替错误处理。

## 2.6.6 函数

- 函数要短，只做一件事。
- 一个函数尽量在一屏内读完。
- 局部变量不要太多，超过 5 到 10 个就考虑拆分。
- 函数之间用空行隔开。
- 参数不要太多；参数过多通常说明应该拆结构体或拆函数。

```c
int max_int(int a, int b)
{
	if (a > b) {
		return a;
	}
	return b;
}
```

这个函数只做一件事：返回两个整数中较大的那个。

如果函数里出现大段注释来解释“第一步、第二步、第三步”，通常说明它可以拆成几个小函数。

## 2.6.7 布尔值和返回值

判断类变量用 `stdbool.h`：

```c
#include <stdbool.h>

bool is_valid = true;

if (is_valid) {
	...
}
```

不要用 `int` 和 `1`、`0` 模拟布尔值，除非在和旧代码或 C 接口交互。

返回值约定：

- 返回错误码的函数：`0` 表示成功，`-1` 表示失败，具体原因放在 `errno` 或输出参数里。
- 返回判断结果的函数：非 0 表示真，0 表示假，返回类型用 `bool`。
- 返回计算结果的函数：直接返回结果；无法计算时要有明确的错误约定。

```c
int save_student(const struct student *student)
{
	if (student == NULL) {
		return -1;
	}
	...
	return 0;
}
```

## 2.6.8 宏

常量宏用大写：

```c
#define MAX_STUDENTS 100
```

函数式宏要加括号，多语句宏用 `do { ... } while (0)`：

```c
#define MAX(a, b) ((a) > (b) ? (a) : (b))

#define LOG_ERROR(msg) \
	do { \
		fprintf(stderr, "%s\n", msg); \
	} while (0)
```

能写函数就不要写函数式宏。宏没有类型检查，参数还可能被重复求值。

## 2.6.9 typedef 和 goto

本书按规范默认不使用 `typedef` 给结构体起别名：

```c
struct student {
	char name[32];
	int age;
};
```

使用：

```c
struct student s;
```

不写：

```c
typedef struct student {
	...
} Student;

Student s;
```

很多教程会使用 `typedef`，因为它能少写一个 `struct`。本书为了和规范保持一致，示例统一使用 `struct student`。第 4 章会解释两种写法的区别。

`goto` 只用于函数内统一的错误清理和退出，不用于普通流程控制。

```c
int load_file(const char *path)
{
	FILE *file = fopen(path, "r");
	int result = -1;

	if (file == NULL) {
		return -1;
	}

	if (/* 读取失败 */ 0) {
		goto out_close;
	}

	result = 0;

out_close:
	fclose(file);
	return result;
}
```

初学阶段先不用 `goto`。等第 5、6 章出现“打开文件、申请内存、失败后要逐层清理”的场景，再回来看这个模式。

## 2.6.10 用工具保持格式

手工保持格式很容易忘。可以用工具自动处理。

`clang-format` 可以按配置格式化 C 代码：

```bash
clang-format -i hello.c
```

仓库根目录会提供 `.clang-format` 和 `.editorconfig`。编辑器支持时，保存文件会自动套用同样的规则。

常用检查命令：

```bash
clang-format --dry-run --Werror examples/chapter2/2.1.1_arithmetic.c
```

`--dry-run` 只检查不修改；`--Werror` 表示格式不符合就返回失败。

> **Windows 提示**
>
> `clang-format` 通常随 LLVM/Clang 安装。Windows 上可以安装 LLVM 或 Visual Studio 的 Clang 工具；如果命令找不到，把安装目录加入 `PATH`，或者使用 VS Code 的 Clang-Format 扩展。

## 2.6.11 重构示例：从能跑到好读

下面这段代码能运行，但不容易读：

```c
int f(int a[],int n){int s=0;for(int i=0;i<n;i++){if(a[i]>0){s+=a[i];}}return s;}
```

问题：

- 函数名 `f` 没有说明用途。
- 变量名 `a`、`n`、`s`、`i` 太短。
- 所有代码挤在一行。
- 没有空格，括号和运算符混在一起。
- 没有注释说明“只累加正数”。

改写后：

```c
// 返回数组中所有正数之和
int sum_positive(const int values[], int count)
{
	int sum = 0;

	for (int i = 0; i < count; i++) {
		if (values[i] > 0) {
			sum += values[i];
		}
	}

	return sum;
}
```

功能没变，但读起来清楚多了。

## 2.6.12 提交前检查清单

- 缩进是否统一为 Tab，宽度 4 或 8。
- 每行是否不超过 100 列。
- 控制语句的大括号是否在行尾，函数大括号是否另起一行。
- `switch` 的 `case` 是否左对齐。
- 变量和函数名是否使用小写加下划线。
- 是否有无意义的缩写。
- 注释是否解释“为什么”，而不是重复代码。
- 函数是否只做一件事。
- 嵌套是否超过 4 层。
- 是否有忘记 `break` 的 `switch`。
- 是否有未处理的错误返回值。
- 是否通过 `clang-format` 检查。

## 2.6.13 代码质量自查清单

前面的清单检查“长得对不对”。这一节的清单检查“结实不结实”——大部分 C 程序的崩溃不是语法错误，而是习惯没养好：忘了检查、忘了释放、下标越界、空指针。

写完一段代码，按这张表过一遍：

| 问题 | 对应章节 |
|------|----------|
| 每个可能失败的地方都检查了吗（`fopen`、`malloc` 的返回值，除数是否为 0）？ | 第 1.5、5、6 章 |
| 用数组时想过边界吗？循环条件是 `i < n` 而不是 `i <= n`？ | 第 3.1、8.4 节 |
| 每个“打开/申请”都有配对的“关闭/释放”吗（`fopen` 配 `fclose`，`malloc` 配 `free`）？ | 第 5、6 章 |
| 指针解引用之前，确认它不是 `NULL` 了吗？ | 第 4.1、6.2 节 |
| 魔法数字都换成有名字的宏或常量了吗（`MAX_STUDENTS` 而不是 `100`）？ | 第 2.6.8 节 |
| 布尔变量读起来像一句话吗（`is_valid`、`has_error`）？ | 第 2.6.4、2.6.7 节 |
| 相关数据组织进结构体了吗？参数太多时用结构体打包了吗？ | 第 4.4 节 |
| 每个变量初始化了吗？声明时就给出初值是省心的做法。 | 第 1.4 节 |
| 如果让别人（或三个月后的自己）读这段代码，能看懂吗？ | 第 2.6 节 |

这张表不是用来背的，是用来在提交前“翻”的。前四条对应的是会直接崩溃的错误，后面几条决定代码能不能被维护。第 6 章讲完动态内存后，可以再回到这张表，把内存相关的条目补进自己的习惯。

B. 所有大括号都放在行尾\

A. `case` 比 `switch` 缩进一层\

#### 三、改错题

三处错误：

1. `case 8:` 忘记 `break`：`85 / 10` 是 8，输出 `良好` 后会贯穿到 `case 7`，多输出 `中等`。提交前检查清单里专门列了这一项。应在 `case 8` 末尾补 `break;`。

3. `main` 结尾漏了 `return 0;`：本书规范要求 `main` 明确写出返回值，保持和其他函数一致的收尾习惯。
